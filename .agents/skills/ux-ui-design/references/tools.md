# Tools by the question they answer

A reference source, editable canvas, generator and browser test provide different
evidence. Select the smallest sufficient combination by relevance, current access
and output needs. Free access is useful, not proof of quality. No paid service or
second coding agent is mandatory.

## Discover capabilities and choose a fallback

At the start, inspect actual callable tools and available browser/shell support.
A saved MCP configuration or published tool list is not a working connection.
For each needed capability record a short row in design.md:

| Need | Available tool/route | Verified action and evidence | Access/cost limits | Fallback or gap |
|---|---|---|---|---|

Check only task-relevant capabilities: reading real screens/ordered flows,
writing an isolated design, exporting local assets/HTML, or exercising the runtime.
For an unverified connection, use a harmless read-only probe before promising an
output. A successful listing establishes discovery, not file editing, export or
usable reference coverage. Preserve existing user projects and sessions.

Use focused public queries and synthetic/redacted fixtures. Do not upload private
texts, account-bearing screenshots or project credentials as a setup test.
Do not print secrets, including credential-bearing server URLs.

If an optional tool is unavailable, use an available source/tool that answers the
same question and name the substitution. Missing a reference cannot be repaired
by generating an imitation. A required named source remains an explicit gap until
actually used; do not claim its output from a fallback. Continue independent work
without indefinite retries, repeated logins or unnecessary installations. Check
regional/account eligibility before setup; transport does not bypass it. For a
login handoff verify a visible browser and use supported owner authentication.

## Select by purpose

| Need | Candidates | Evidence/output |
|---|---|---|
| Current task and redesign baseline | Existing product, code/tests, Chrome DevTools | Actual path, observed friction, strengths and relevant local version |
| Real reference flows | Accessible live products/recordings, relevant Screenrove or Mobbin captures | Inspected screens/order, mechanism, tradeoff and coverage gaps |
| UX structure | Simple wireframes; available editable canvas or UX Pilot when useful | Different paths only when structure is uncertain; same task comparison |
| Editable UI/design-system work | Penpot, Figma or installed Open Design when accessible | Editable design and explicit mapping to DayEnglish tokens/components |
| HTML authoring | Local HTML; isolated React for complex state; suitable available authoring tool | Local HTML entry/assets with working task interactions |
| Runtime checks | Chrome DevTools, available Playwright/browser automation | Actual rendering, state transitions, keyboard and recovery evidence |
| Automated a11y rules | Available axe-core integration plus manual checks | Scoped findings, not an accessibility or UX score |
| Understanding by people | Moderated observation; Maze when useful and accessible | Actual task completion, wrong turns, interpretation and assistance |

Prefer useful evidence and existing capabilities over setting up another service.
A missing optional canvas/generator is not a reason to stop an HTML deliverable.
Specialised generation does not replace task discovery, UX synthesis or user tests.

## Screenrove: reference candidate

[Official agent guide](https://screenrove.com/agents) documents an account-free
remote MCP, screen captures, measured design guides and captured journeys.
Verify current access, tool schemas and relevant coverage. Inspect scope labels,
dates and images: marketing, public-demo, signed-in and incomplete captures are
different evidence. Do not assume a needed translator/reader flow is present or
treat a generated handoff/check_my_ui critique as observed user behavior.
Adapt interaction mechanisms; keep DayEnglish's own design system.

## Mobbin: optional reference library

[Overview](https://mobbin.com/mcp), [features](https://docs.mobbin.com/mcp/features),
[access/credits](https://docs.mobbin.com/ai-credits),
[official search/redesign skills](https://github.com/mobbin/skills).

MCP requires an eligible paid plan; verify current terms/access. Lack of an account
today is not a permanent rejection by the owner. Prefer flow retrieval for order
questions and screen retrieval for states, discovering the actual schemas.
Inspect the images and keep source IDs/links; previews can omit steps and image
URLs expire. Many captures from one product are not independent examples. Do not
use unofficial cookie scrapers or confuse REST API access with MCP access.

## Penpot: optional editable canvas

[Official MCP guide](https://help.penpot.app/mcp/),
[pricing](https://penpot.app/pricing), [prototyping](https://help.penpot.app/user-guide/prototyping-testing/prototyping/).

Useful when editable boards, components/tokens or collaborative visual revision
are needed. Verify current limits: a free cloud plan/MCP does not imply unlimited
storage, history, inference or free self-host operation.

Remote MCP requires account setup, a personal key and an active connected file/tab;
local mode adds a running server/plugin. The current focused page determines the
write target: inspect context before editing an isolated file. The remote server
URL may contain a credential; keep it out of records and prototypes. Remote/local
asset import/export capabilities differ, so check the needed handoff explicitly.

Board transitions and inspectable HTML/CSS do not prove a working app prototype.
Arbitrary input, async state, persistence, offline/recovery and keyboard focus need
a real HTML runtime. Use Penpot for its editing benefit, not as a prerequisite or
an automatic UX improvement. Prefer current official docs over archived servers.

## Other authoring/test candidates

[Stitch](https://stitch.withgoogle.com/) and [UX Pilot](https://uxpilot.ai/) may help
explore candidates; check actual eligibility, generation and export access first.
Do not default to a known-unavailable service. [Figma Make](https://www.figma.com/make/)
or installed Open Design can support detailed authoring when the needed capability
works. [Maze](https://maze.co/features/prototype-testing/) can organise task tests;
forecast heatmaps and AI critiques are not observations of people.

[Playwright accessibility guidance](https://playwright.dev/docs/accessibility-testing)
describes axe integration and its manual-testing limits. Reuse existing automation;
do not add root dependencies just to make an optional scan available.
